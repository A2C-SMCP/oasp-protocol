# Protocol Design Review — 协议接口设计评审

> 目标不是"字段能不能传"，而是"这个接口是否让协议在**十年尺度**上保持抽象一致、表面干净、双端零映射易实现"。
>
> **这个 skill 存在的理由**：工程师在紧张的开发节奏下，最先丢掉的是**抽象判断力**——为了尽快响应 Feature Requestor，把需求逐条翻译成零散参数怼到接口上，短期能交付，长期让协议腐化成"一大堆扁平字段的堆砌"。本 skill 是一次**强制的冷静**：在合并前，用固定的 rubric 逼自己回答"有没有更优雅的实体抽象"。宁可慢十分钟，不要给协议留十年的债。

---

## 何时触发

- 新增 / 修改协议事件（`{namespace}:{action}:{target}`）或数据结构（`data-structures.md`）。
- 评审协议 PR（尤其"新增能力""补齐字段"类）。
- 设计新接口、拿不准"该拆几个接口 / 每个接口放多少参数"。
- 感觉自己在"照着需求清单一条条加字段"——**这正是最该停下来跑本 skill 的时刻**。

本 skill 只审**协议接口设计**（抽象、语义、一致性）。代码实现质量走 `a2c-smcp-toolkit:code-review`；协议字段可行性走 `a2c-smcp-toolkit:cross-ask`（二者用 Skill 工具调用）。

---

## 🚨 开发压力下的红线（先自查这 6 条，命中任一 = 停下重想）

在深入 rubric 前，先扫这份"醒脑清单"。命中任何一条，说明你可能正被节奏压着走：

1. **同一接口/结构上出现 ≥3 个同族扁平字段**（`fontSize` / `fontName` / `fontColor` / `bold` / `italic`…）→ 该抽实体了，不是继续加字段。
2. **正在给一个已有实体的"另一处用法"重新平铺一遍相同字段**（整框级一套、run 级又一套）→ 应复用同一实体，不是复制。
3. **理由是"Requestor 就要这个字段" / "先交付了再说"** → 需求方视角 ≠ 协议架构视角，见 Step 3。
4. **Draft 命名空间里，一边加新结构一边留一堆 `Deprecated` 别名兼容** → Draft 应 clean-break 直接删旧字段，别背兼容包袱（Step 6）。
5. **新枚举/结构是从别的命名空间"顺手抄"来的**（PPT 抄 Word 的 underline）→ 跨命名空间要零映射对齐各自宿主，"抄"往往制造错配（Step 4）。
6. **没问过宿主能力就定字段** / **没标 requirement set 与降级** → 可行性与版本门槛未定，接口就是空中楼阁（Step 5）。

> 命中不等于错，等于**需要一个显式的、写进 PR/changelog 的理由**。说不出理由，就是债。

## Step 1：确定评审范围

| 输入 | 取变更方式 |
|------|-----------|
| 无参数 | `git diff main...HEAD` + 工作区 `git diff` |
| PR 编号 | `gh pr diff <n>`；正文用 `gh pr view <n>` |
| 事件名 / 结构名 | 在 `docs/specification/` 内定位其定义与所有引用点 |
| 文件路径 | 直接审该文件 |

**读完整定义，不只读 diff**：一个字段是否散堆、是否该复用某实体，往往只有把 `events-*.md` 与 `data-structures.md` 对照着看才能判断。列出：本次新增/改动的**事件**、**数据结构**、**枚举**、**错误码**，及它们的**复用点**。

---

## Step 2：抽象层级与实体收敛（本 skill 的核心）

这是最重要的一步。逐条审：

### 2.1 散堆检测 → 实体收敛
- 有没有一族语义相关的扁平字段被平铺在事件/结构上？（字体、位置、边框、填充…）
- 能否收敛成**一个可复用实体**（如 `PptFont`），让事件只挂实体、不挂散字段？
- 该实体是否在**多处复用**（整框级 / run 级 / 表格单元格 三处共用同一 `PptFont`）？复用度越高，抽象越值。

### 2.2 接口数量 vs 单接口参数量的平衡
- 新增能力，是靠"加事件"还是"给现有事件加嵌套实体/数组"实现的？
- 优先**更少接口 + 更富的嵌套实体**（run 级格式挂在 `update:textBox` 的 `runs[]`，而非另开 `update:run` 事件）。
- 反问：如果这个能力用一个 `{start, length, payload}` 的区间寻址模式就能承载，就别为它新增顶层接口。

### 2.3 实体内聚 vs 散堆的区分
- 一个实体有 12 个字段**不是**散堆——只要它们**高内聚**（都是"字体"维度）。散堆是指**跨维度的零散字段平铺在事件根上**。
- 判据：这些字段是否会**一起出现、一起演进、语义同族**？是 → 收进实体；否 → 可能是不同关注点，别硬塞一个实体。

### 2.4 关注点分离
- 不同维度别混进一个实体：字体格式 ≠ 对齐（段落/单元格级）≠ 几何（位置尺寸）。
- 例：表格单元格的 `horizontalAlignment` 是单元格级、`font` 是字体级 → 分开挂，不并入 `PptFont`。

---

## Step 3：Feature-Request 纪律（不一味响应需求方）

- **需求方视角 ≠ 协议架构视角**。Requestor 要的是"我这个场景能用"；协议要的是"整体一致、可长期演进"。
- 每个字段问四问：**架构合理性**（是否破坏已有抽象）·**抽象合理性**（是否该收进实体）·**功能丰富性**（是否真被需要，还是过度设计）·**可行性**（宿主是否支持，见 Step 5）。
- **敢划范围边界、敢砍**：把宿主不支持的、走另一条技术路径的（如 OOXML 而非 office.js）、属于别的关注点的，明确列进"范围边界（不含）"并说明去向。范围边界写不出来，往往是没想清楚。
- **敢反推需求方的版本/事实假设**：Requestor 提的 requirement set、枚举值数量可能是错的——本项目历史上就纠正过 office4ai#45 的多处版本误标。以宿主复核为准。

---

## Step 4：跨命名空间一致性（零映射对齐宿主）

- `/word`（Word.js）、`/ppt`（office.js PowerPoint）、`/excel` 服务**不同宿主 API**。
- **同名概念，不同命名空间可以、且往往应该有意不同**：PPT `ShapeFontUnderlineStyle`（17 值 PascalCase）≠ Word `UnderlineStyle`（7 值小写）；PPT 对齐 `Center`/`Justify` ≠ Word `Centered`/`Justified`。各自**零映射对齐宿主枚举**，双端直接 cast。
- **红线**：从一个命名空间"抄"结构/枚举到另一个 → 极易制造宿主错配、映射 bug。跨命名空间复用只在"底层宿主 API 确实同源"时才成立。
- **有意不同必须写成文档**（admonition），标为"有意的跨命名空间差异，非命名不一致"——否则后人会当 bug"修"回去，或误抄。

---

## Step 5：可行性 · 版本门槛 · 降级语义

### 5.1 可行性先行（协议先行流程的一环）
- 定字段前先 `/cross-ask office-editor4ai`（office.js / Add-In）→ 不行再问 `office4ai`（OOXML 离线）→ 都不行才砍。
- 走 Server 离线路径的字段，事件文档须标**延迟/副作用** admonition。

### 5.2 requirement set 分档必须标注
- 每个能力标注最低宿主 requirement set（如 PowerPointApi 1.4 / 1.8 / 1.10）。
- **注意访问器抬平**：同一实体在不同承载点门槛可能不同——`PptFont` 在文本框是 1.4/1.8 分档，在**表格单元格**因 `TableCell.font` 访问器被**统一抬平到 1.9**。别照抄门槛，按承载点复核。

### 5.3 降级 = 反应式、全或无、无"部分成功"
- 宿主能力/版本不足或目标非法 → 事件**整体失败**（`3016 API_NOT_SUPPORTED` / `4002 INVALID_PARAM`），`details.requiredApiSet` 标版本。
- **不引入"部分成功"语义**：如"跳过非法单元格继续"是反模式，应改为**前置校验 + 命中即整请求失败**（含合并单元格空对象 / 区间越界）。
- 版本握手 ≠ 运行时能力：能力不足在**操作期反应式**处理，不靠握手。

### 5.4 枚举承载分档
- **小而封闭的集合 → 就地全枚举**（underline 17 值、对齐 7/6 值）：可校验、稳定。
- **大而易变的宿主枚举 → 直通 `string`**（bullet `style` 40+ 值）：由宿主校验、非法 → `4002`。
- 二者同为"零映射对齐宿主"，形态按**集合规模与稳定性**分档——这是一致原则，须在文档里点明，避免被当成不一致。

## Step 6：约定合规 · 兼容性 · changelog

### 6.1 命名与结构约定（见 CLAUDE.md）
- JSON 字段 camelCase；事件名 `{namespace}:{action}:{target}` kebab-with-colon；错误码 SCREAMING_SNAKE。
- 请求含 `requestId`/`documentUri`/`timestamp?`；响应含 `success` + `data`|`error`。
- 错误码分段：1xxx 通用 / 2xxx 连接鉴权 / 3xxx 文档操作 / 4xxx 校验。**优先复用既有错误码，别为每个新校验造新码**。
- 文档从简：TypeScript interface 注释足矣，避免冗长字段描述表。

### 6.2 兼容性（Draft vs Stable 两套判断）
- **Draft 命名空间**（`/ppt`/`/excel`）：无稳定性承诺 → 收敛应 **clean-break 直接删旧字段，不留 `Deprecated` 别名**，避免协议表面长期背散堆。
- **Stable 命名空间**（`/word`）：破坏性变更需**单独 cross-ask + 独立 PR**，不可混进别的 feature PR；能兼容则加可选字段 + 明确迁移路径。
- 判断"这是不是破坏性变更"，并在 changelog 如实标注（别把破坏性收敛写成"向后兼容"）。

### 6.3 changelog 纪律（见记忆 Version Management）
- 大变更累积到 `[Unreleased]`（目标下一个 MINOR），**不主动 deploy**，等用户手动发版。
- 条目要覆盖：变更表、requirement set 分档、降级语义、跨命名空间说明、兼容性、范围边界。

## 输出格式

按严重度排序输出结论，每条：

```
[级别] 位置 — 一句话问题
  现状：<当前设计>
  建议：<更优抽象/收敛/修正>
  理由：<对照 Step 2–6 的哪条原则>
```

级别：
- 🔴 **架构债**：散堆未收敛、跨命名空间错抄、部分成功语义、Draft 留兼容别名 → 合并前必改。
- 🟡 **需显式理由**：命中红线但可能有合理权衡 → 要求在 PR/changelog 写清理由。
- 🟢 **一致性/文档**：缺 requirement set 标注、缺"有意不同"admonition、命名不合约定。

结尾给一句**总体判断**：这个接口是否让协议更健康；若有 🔴，明确"先改再合"。

> 若本次评审催生了跨仓工作（工具侧实现、其他命名空间的同类收敛），提示用户：协议先行合并后，去工具仓库（Add-In 实现在 `JIAQIA/office-editor4ai`、MCP schema 在 `A2C-SMCP/office4ai`）建实现 issue。
